# Ducky One 3 SF RGB V4 hardware readiness

## Recommendation

**NO-GO for hardware programming.** The revised candidate passes the independent raw-image instruction audit. Three release gates remain open. The LDROM programming limit and erase behavior for the additional APROM pages are unknown, no APROM-independent recovery route has been demonstrated, and neither complete SRAM writer coverage nor a runtime worst-case stack margin has been established. Real endpoint arbitration and keyboard/LED timing also need bench evidence. The proposed programming profile below is disabled. All work here was offline.

## Candidate identity and binary audit

Ghidra MCP was attached to the stock V1.16 project, at base zero, and returned the stock SHA-256 and bytes at all nine patch locations. Its tool surface has no program import or selection operation. A separate headless Ghidra project imported the actual revised V4 raw file. The audit script derives control-flow targets from that file and compares its stock prefix byte-for-byte against the stock image, independently of the build manifest. It checks the alignment fill, scatter descriptor, Thumb vector bit, hook instructions, literal addresses and destinations. [Raw-image audit script](../../tests/AuditDuckyV4.java)

**High confidence.** Independent Ghidra decoding accounted for 1,481 Thumb instructions, 330 direct branch/call edges and 78 referenced literal words in `[0xA7C0,0xB510)`. It also resolved the eight entries of the compiler's bounded switch at `0xAFBA`, whose table is at `0xAFBC–0xAFC3`. The absolute Thumb continuations resolve to `0x321D/0x8931/0x5747/0x9E01/0x3F8F/0x9F27/0x963D`. Non-instruction bytes are the switch table, namespace/constant data at the tail and alignment/pool padding. No literal overlaps executable instructions. The stock prefix differs only in the nine allowed windows, and `0xA7BE–0xA7BF` is `FF FF`.

The incoming compositor loads leave APSR unchanged in stock. The veneer changes flags, but fall-through starts with `MOVS`, and the stock page computation sets condition flags again before a conditional consumer. The other BL sites allow flags to be clobbered under the call ABI, and IRQ return restores the hardware-stacked xPSR. Veneers preserve the required callee-saved registers and stack alignment. There are no new flash, boot configuration or LED driver calls in the extension.

**Stock behavior delta.** The scheduler, renderer, scanout, keyboard scanning, and vendor command handler remain reachable with external mode disabled. The USB path still changes in native mode. Short non-V4 reports are dropped, valid full-length stock replies use a new helper, the wrapper reads bus state before stock acknowledgment, and initializing/checking guards and tracking ownership add execution time. The corrected helper validates segment, epoch and ownership before any write, and masks interrupts through the bounded 64-byte packet copy and arm. The mask cannot stop the USB peripheral itself. Timing, exact W1C behavior and physical endpoint ownership while stock and V4 traffic overlap remain unverified.

## SRAM reservation and writer analysis

Physical SRAM is `[0x20000000,0x20005000)`, 20 KiB. Stock startup decodes `[0x20000000,0x20000414)` and clears `[0x20000818,0x20002820)`. The patched startup clear ends at `0x20002D20` exclusive. The reservation starts at the old zero boundary and is 8-byte aligned. It holds two pitched 228-byte RGB8 pages, a 452-byte RGB16 area, two 64-byte mailboxes, 240 bytes of state/padding, and a four-byte tail guard. [Memory map and stock reference audit](memory-map.md)

The audit fixed a window in which the vendor parser and compositor could use an invalid frame selector before the foreground supervisor detected it. The parser and compositor now check guard state at the use sites and bound local index snapshots before deriving addresses. On detection, the handler latches a fixed-address V4 fault, revokes the session and waits for any pending page to drain before native composition resumes. It neither follows the invalid frame selector nor clears arbitrary SRAM. Capability and unauthenticated status queries remain available. Canaries at `0x20002901/29E5/2BAA/2D1C` detect selected writes. A clobber elsewhere, a valid-looking selector or a sufficiently broad overwrite can escape detection. V4 runtime state is never treated as a protection boundary.

### Stack

The initial vector MSP is `0x20000818`. Normal PUSH and exception entry descend, so the stack top begins `0x2008` bytes below the V4 reservation and normal growth increases that separation. The collision ceiling with lower initialized stock data is 1,028 bytes; it is a capacity limit and gives no evidence about peak use. The main foreground frame at `0x8E52` is eight bytes. Identified simultaneous stock paths include 156 bytes across main, scheduler and mode 10 before its callees, 160 bytes on a settings reset path, and an 88-byte USB SETUP exception witness. The reset-plus-USB witness is at least 248 bytes and can be larger. Cortex-M0 stacks 32 bytes per hardware frame with up to four alignment bytes. TIMER1, TIMER2, TIMER3, SPI0 and USBD are enabled stock vectors. Four programmable priority levels cap configurable nesting, so they can contribute at most 144 hardware-frame bytes by themselves, before software frames or exceptional fault/NMI handling. TIMERS 1/2/3 use up to 24/8/16 software bytes in the traced V4 paths before hardware stacking. TIMER1 calls the 16-byte `0x3A18` routine and the leaf `0x3644`. TIMER2 calls leaf `0x4BDA`. TIMER3 adds the eight-byte veneer before its leaf. Equal priorities would prevent configurable nesting, but live priorities and bootloader handoff have not been observed. [Arm Cortex-M0 guide](https://documentation-service.arm.com/static/5ea6ce5e9931941038def8c1)

The revised image uses 56 local bytes in vendor foreground plus 32 in commit and up to eight in the corruption helper. The compositor adds 16 for its veneer and 32 for its C frame, with another eight on its fault path. Supervision adds eight for its veneer, 16 for C and eight on its fault path. USB entry adds at most 24 temporary bytes before tail-calling the stock ISR. These direct extension paths are bounded and have no recursion or variable-size stack allocation. Stock outgoing frames, reentrant callbacks and unresolved indirect stock calls prevent a whole-program maximum. The known interrupt vector and call graph cannot exclude a stock stack collision below the MSP.

**Watermark plan.** First collect read-only SWD MSP, PSP, CONTROL, IPSR, PRIMASK and NVIC priorities on the stock board, including leaf/prologue checkpoints and overlapping interrupt load. Record the minimum SP and event identity externally. Use hardware execution breakpoints and available write watchpoints only after confirming debug attach and that the tool never unlocks. If a separately authorized diagnostic image becomes justified, write a minimum-SP counter and context tag only into already reserved, aligned V4 bookkeeping and sample at selected deep paths and IRQ entry after accounting for the probe's own stack. This records only the paths sampled and can miss deeper unobserved transients. Use an event-to-coverage matrix and compare scan timing with instrumentation removed. Do not fill the stock stack gap or unused-looking SRAM with a pattern. Halt on a guard failure, a write into the reservation by stock, SP at or below `0x20000414`, or loss of debug control.

## Updater, flash envelope and disabled profile

The local official `Ducky_One_3_SF_RGB_V1.16.exe` is a 1,858,048-byte managed PE with SHA-256 `cae6e350762b7eb5ecf82d4213aba2fde3d9fc974933675b80d930bdbaa863cc`. It embeds the exact stock image once, at file offsets `[0x1A9F68,0x1B4726)`. Offline IL disassembly shows `LdmodeCmdUpdateImage` writes A0 and length at offsets 12–15, sets destination bytes 8–11 to zero, and puts the first 48 bytes at 16. `LdmodeCmdKeepUpdateImage` copies at most 56 bytes per report from offset 8 and stops at image length. `LdmodeReadProcess` sends AB after transfer completion. A3 is declared as an erase-all constant but is absent from the traced updater image flow. Those host methods do not expose the LDROM implementation of A0, including erase scope and handling of tail padding. [Repository LDROM protocol](../firmware.md#8-nuvoton-bootloader-protocol)

| Image | APROM byte range, inclusive | Last 2 KiB page | Pages intersected | A0 reports | Final payload / zero padding in Linux plan |
|---|---|---|---:|---:|---:|
| V1.16 | `0x0000–0xA7BD` | `0xA000–0xA7FF` | 21 | 767 | 54 / 2 |
| V3 | `0x0000–0xA84B` | `0xA800–0xAFFF` | 22 | 770 | 28 / 28 |
| Revised V4 | `0x0000–0xB50F` | `0xB000–0xB7FF` | 23 | 828 | 48 / 8 |

V4 needs one additional page compared with V3 and two compared with stock. Its final report contains image bytes starting at `0xB4E0`; the Linux packet planning code pads the unused eight bytes and excludes them from the declared length. Physical APROM capacity is `[0,0x40000)`, native page size is `0x800`, LDROM is `[0x100000,0x101000)`, and SPROM is `[0x200000,0x200800)`. The user configuration aperture starts at `0x300000`, with CONFIG0 and CONFIG1 at +0 and +4. CONFIG0 bit 0 is clear, indicating Data Flash is enabled. CONFIG1 gives DFBA `0x00033200`, so the nominal shared Data Flash interval is `[0x33200,0x40000)`. Native accesses include settings at `0x33A00/0x34200/0x3F800`. DFBA lies inside an erase page. This audit makes no assumption about writing the boundary page. The requested image and its last page are well below these locations and outside LDROM, SPROM and the separate configuration address space. This is an address calculation. LDROM's effective write ceiling, acceptance of 828 reports, configuration protection and physical erase scope still require LDROM analysis or independent recovery before testing. The offline linker ceiling `0xC7C0` is a builder limit. The preserved APROM-to-LDROM path is not a read-only inspection. At `0x8B54–0x8BA0` stock reads a validation word at `0x3F800`, checks the stock magic from `0x8DD4`, calls the flash erase/write helpers with page size `0x800`, changes the boot selection and requests system reset. Any future read-only audit must avoid invoking this reboot path. Loader read-only identity inspection requires already being in LDROM. The existing recovery tools enforce stock/V3 profiles. Their partial-transfer failure path leaves the loader available if it still responds and skips AB and automatic retry. A pure packet-plan round-trip verified the 828 reports, declared length and final padding. The Linux acknowledgement sequence would run from 4 through 1658 inclusive in steps of two, subject to actual LDROM acceptance. Both existing image profiles reject the V4 file. No V4 profile was added.

## Recovery evidence and bench prerequisites

The recorded CONFIG0 encodes CBS = `01`, which the NUC1261 header describes as LDROM boot without IAP. This supports a cold-start LDROM handoff, but says nothing about whether vendor LDROM exposes HID or immediately jumps to APROM when the application is invalid. The value also has LOCK bit 1 clear, which indicates protected readout under the documented CONFIG layout. Independent SWD attachment, permission to read flash and permission to restore APROM are separate prerequisites. Confirm the raw config and protection status without any unlock. [NUC1261 boot and ISP status definitions](https://raw.githubusercontent.com/OpenNuvoton/NUC1261BSP/master/Library/Device/Nuvoton/NUC1261/Include/NUC1261.h#L1986-L2002) · [Nuvoton configuration layout](https://www.nuvoton.com/resource-files/TRM_NUC126_Series_EN_Rev1.03.pdf)

| Failure | Available evidence and action under separate authorization |
|---|---|
| RGB state corrupt, APROM still functional | Firmware guard can revoke external mode. Cold power cycle clears V4 state. The original vendor command remains reachable in the binary. Live V4 recovery has never been demonstrated. |
| APROM enumerates and handles the stock reboot command | The USB transition to LDROM and stock V1.16 restoration from V3 were demonstrated. Verify the exact loader profile and fallback image before using that path. Shorter stock restoration leaves the condition of added APROM tail pages unread. |
| APROM cannot enumerate, crashes or cannot process commands | No repository test shows forced LDROM entry with dead APROM. Normal power cycling may simply retry APROM. The Ducky manual was checked for a loader-entry procedure. Its factory-reset chord is not evidence of an APROM-independent path. No keyboard chord or strap is established as an independent loader entry. [Ducky One 3 RGB manuals](https://ducky.global/products/one-3-rgb) |
| Programming stops midway | If exact LDROM still enumerates, inspect its identity and retain it in loader mode. A complete restore after deliberate interruption has not been demonstrated. If the loader is gone, the APROM reboot route may already be unavailable. |
| USB recovery unavailable | SWD/ICP and connect-under-reset are candidates. Locate and verify SWDIO, SWCLK, nRESET, GND and reference voltage; confirm target and read/security behavior with a qualified probe that has automatic erase/unlock disabled. Protection may prevent backup or non-destructive recovery. The existing hardware path is untested. |

Before asking to program V4, establish either proven independent LDROM entry or a recoverable, protected-region-aware programming path on suitable hardware. Obtain read-only identity, configuration, and permitted backup/readback evidence for APROM, LDROM, Data Flash and configuration. Verify what A0 erases and whether restoring the stock length erases the V4-only pages. Exercise stock under watchpoints or suitable trace with multiple profile/effect/macro inputs, USB lifecycle and known callback paths, and establish the stack low-water margin. Then validate an explicitly approved candidate in native mode before running external frame, overlay, reconnect and timing checks. Use a separate input device. Stop on identity mismatch, programming acknowledgement loss, unexpected flash range, loss of USB input, guard fault, reset, unaccounted store, or persistent scan jitter. No V4 bench activity has been performed. [Stock recovery limits](../../tools/recovery/README.md#limits) · [Hardware recovery prerequisites](../../tools/recovery/hardware-recovery.md)

## Offline execution coverage

The headless Ghidra harness executes candidate instructions through scatter initialization, the patched USB event/vector and OUT path, foreground service, stock compositor and stock page selection. It tracks writes against an explicit allowlist. The deterministic seed is `0xD0C42026`. The long Thumb run passed 2,000 staged, committed and displayed frames with new randomized RGB, incomplete and malformed requests, duplicate/reordered chunks, and repeated mode transitions. The lowest stack write in that run was `0x20000740`. No traced write exceeded the path allowlist. In the expanded 32-frame run, all masked overlays and corrupt-selector fallbacks were exercised, including a native mode-init and profile-render publication, synthetic suspend/resume indications, the lease boundary, sequence exhaustion, and the stock reset veneer continuation. The lowest observed stack write was `0x20000738`, 168 bytes below the fixture SP of `0x200007E0`. The native C routine and host suite passed all 15 tests. ASan and UBSan also passed for the C harness, including all 240 order/commit-form combinations, a 2,000-frame consecutive commit run, and exhaustive channel scaling. It models USB and SPI register state and inserts events between calls. It does not reproduce real asynchronous exception entry, W1C timing, the whole main loop, LDROM, profile persistence/flash execution, physical overlays, or a fully timed scanout. In particular, an IRQ can arrive after the compositor checks the bus epoch and before the stock publish store at `0x3F8C`. Foreground revocation on the next pass is known, while same-sweep presentation or blanking in that window remains untested. Overlay mask coverage means each mask was accepted and passed to the compositor harness. The fixture does not assert every stock overlay pixel with live profile records.
